# 第 4 章「AI 时代对架构的要求」详细课程设计

## 一、章节总体设计

### 1.1 设计理念

本章从"为什么 CPU 跑不动大模型"出发，经历"GPU 为什么够但还不够"、"NPU/CANN 如何重新设计"、"如何榨干单芯片性能"，最终走到"单芯片极限→超节点"。每个技术点都嵌入到真实场景中，避免抽象概念的孤立讲授。

### 1.2 三节课故事线

```
第 4.1 课：大模型来了，CPU 为什么不行？
  └─ 场景：工程师拿到一个 7B 模型，在 CPU 上推理要 30 秒/句，无法上线
     ├─ 问题 1：大模型到底在算什么？（算子特征）
     ├─ 问题 2：数据量和访存有什么不同？（存储/访存特征）
     ├─ 问题 3：CPU 的优化手段为什么失效？（无法满足计算和访存要求）
     ├─ 问题 4：GPU SIMT 是最终答案吗？（GPU 演进 + 辩论）
     └─ 结论：需要新的架构和编程模型 → 引出下节课 CANN

第 4.2 课：CANN 如何重新设计架构？
  └─ 场景：工程师拿到昇腾 950，发现硬件完全不同——三核、UB、L0A/B、NDDMA
     ├─ 维度 1：计算单元——为什么要三核异构？（AIC/AIV、SIMD/SIMT）
     ├─ 维度 2：存储层次——为什么软件管理 UB/L0A/L0B/L0C/Reg (多级存储)
     ├─ 维度 3：数据搬运——对齐/非对齐/ND/NZ Layout/NDDMA 是什么？（搬运有哪些特点和要求？）
     ├─ 维度 4：编程模型——从 Ascend C 到 PyPTO，为什么要分层？（怎么平衡易用性与性能，分层暴露体系架构？）
     └─ 结论：四个维度都是体系结构经典原理的 AI 实现

第 4.3 课：如何榨干性能？从单芯片到超节点
  └─ 场景：工程师的算子在 950 上只跑到峰值算力的 40%，如何优化到 90%+？
     ├─ 优化 1：数据与任务规划——怎么切分数据和任务？（多核并行、负载均衡）
     ├─ 优化 2：流水并行——计算和搬运怎么重叠？（Double Buffer 、UnitFlag）
     ├─ 优化 3：访存优化——对齐/Layout/预取怎么选？（访存优化）
     ├─ 优化 4：计算优化——标量/矢量/矩阵怎么协同？（Reg VF融合等）
     ├─ 回归：四个优化维度对应四个体系结构原理
     └─ 超越：单芯片极限 → 超节点（SuperPod）→ 引出第 5 章多卡互联
```

---

#### 时段 1：大模型到底在算什么？——计算特征分析

**内容设计**：

1. **大模型算子族拆解（10 分钟）**：
   - 以 Transformer 为例，逐层拆解计算量占比：
     - **矩阵乘（GEMM/MatMul）**：~60-70% 计算量（QKV 投影、FFN、Attention 中的 QK^T 和 AV）
     - **逐元素运算（Elementwise）**：~10-15%（激活 Add/Mul、残差连接、Bias）
     - **归约运算（Reduce）**：~5-10%（Softmax 中的 max/sum、LayerNorm 中的 mean/var）
     - **数据搬运/布局变换**：~10-15%（reshape、transpose、concat、split）
   - **关键洞察**：大模型 ≈ 矩阵乘 + 少量逐元素/归约 + 大量数据搬运。计算模式高度规则且固定。

2. **计算密度（Arithmetic Intensity）概念（10 分钟）**：
   - 定义：每字节数据支撑多少次浮点运算（FLOPs/Byte）
   - **计算密集型算子**：GEMM、Conv——计算密度高（>100 FLOPs/Byte），瓶颈在算力
   - **访存密集型算子**：LayerNorm、Softmax、激活、逐元素 Add——计算密度低（<10 FLOPs/Byte），瓶颈在带宽
   - **Roofline 模型**：用一张图展示——横轴计算密度，纵轴性能，两条线（带宽墙 + 算力墙），不同算子落在不同区域
   - **类比**：计算密度像"做菜时每买一次菜能做多少道菜"。GEMM 是买一次菜做 100 道菜（计算密集），LayerNorm 是买一次菜只做 1 道菜（访存密集）。

3. **概念测试题 2（Peer Instruction，5 分钟）**：
   > **问题**：以下哪个算子最可能是访存密集型（瓶颈在显存带宽）？
   > - A. 7B 模型中的 FFN 矩阵乘（4096→11008→4096）
   > - B. LayerNorm 归一化
   > - C. 卷积层 3×3 Conv（stride=1）
   > - D. 两个 4096×4096 矩阵相乘

4. **大模型计算特征总结（10 分钟）**：
   - **特征 1**：计算高度集中在少数几类算子（GEMM 为主），模式规则
   - **特征 2**：计算密度两极分化——GEMM 计算密集，归一化/激活访存密集
   - **特征 3**：数据搬运（layout 变换、reshape）占比不可忽视
   - **回归体系结构原理**：**工作负载决定架构设计**——既然计算模式这么规则，为什么还要用通用 CPU 的乱序执行和硬件 Cache？专用化是不是更高效？（埋下 NPU 的伏笔）

---
#### 时段 2：大模型的数据和访存有什么不同？——存储与访存特征

**内容设计**：
1. **数据量跃迁**：
   - **通用程序**：工作集 KB~MB 级（一个 Web 服务、一个编译器），能放进 L2/L3 Cache
   - **大模型训练/推理**：
     - 模型参数：7B 模型 FP16 = 14GB，70B = 140GB，MoE 专家参数 TB 级
     - 激活值：batch=32, seq=2048, 7B 模型中间激活 ~数十 GB
     - 梯度/优化器状态：训练时是参数的 4~8 倍（AdamW：参数+梯度+m+v）
   - **关键数据**：GPT-3 175B 训练一次，总数据搬运量 > 1 ZB（10^21 字节），相当于全人类说过的所有话的文本量的数倍
   - **类比**：通用程序的访图像"从家里冰箱拿菜"（几步路），大模型的访图像"从全国冷链仓库调菜到餐厅"（几千公里，必须用大卡车+物流规划）

2. **访存模式变化（10 分钟）**：
   - **通用程序**：访存不规则——依赖控制流（if/else）、指针 chasing、递归，硬件预取器只能识别简单步长模式
   - **大模型**：访存**高度规则且编译时可知**——
     - GEMM：按分块（tiling）规则读取矩阵块，访问模式完全可预测
     - LayerNorm：按行/列顺序扫描，连续访问
     - Attention：按 head 分块，规则访问
     - 唯一不规则：MoE 路由（token 到不同专家）、动态形状（seq len 变化）
   - **关键洞察**：当访存模式从"不可预测"变为"编译时可知"，**硬件自动管理的优势（通用性）就变成了劣势（不精准、有开销）**。软件可以比硬件预取器更精准地安排数据搬运。

3. **计算与访存可静态分离（7 分钟）**：
   - **通用程序**：计算和访存交织在一起（load→compute→store→load...），难以静态分离
   - **大模型算子**：计算和访存可以**静态分离**——
     - GEMM：先把一个 tile 的数据全部加载到片上，然后纯计算（不访存），计算完写回
     - 这意味着**计算和搬运可以完全重叠**：算当前 tile 的同时，搬下一个 tile
   - **类比**：通用程序像"边炒菜边去买菜"（炒一半发现没葱，关火去买），大模型像"提前把所有菜备好在灶台边，然后专心炒"（备菜和炒菜可以并行）

4. **小组讨论：CPU 架构是否可以满足AI计算诉求 ？（10 分钟）**：

 - 针对这些AI计算和仿真特征，CPU是否可以满足诉求？
 - **若不满足，期望的架构是啥样的**？


#### 时段 3：从 CPU 到 GPU SIMT——是最终答案吗？

**内容设计**：

1. **从CPU到GPU SIMT（8 分钟）**：
   - **SIMT（Single Instruction Multiple Threads）**：一个 Warp（32 线程）执行同一条指令，数据并行

2. **Mini 辩论：SIMT 是不是最终编程模型？（10 分钟）**：
   - **辩题**："面向大模型时代，SIMT（单指令多线程）是不是最终的编程模型？还需要新的编程模型吗？"
   - **正方（SIMT 够用）**：
     - CUDA 生态成熟，库和工具链完善
     - SIMT 足够灵活，能处理各种算子
     - 程序员已经熟悉，迁移成本高
   - **反方（需要引入新架构）**：
     - SIMT 控制开销大，专用架构需要新编程模型
     - 大模型算子规则，更高层的抽象（Tensor/Block）更高效
     - 多卡/超节点时代，SIMT 不适合表达分布式计算

3、**现代GPU架构演进**
  - 越来越多的专用计算单元和数据传输单元，如Tensor Core、TMA等；

**设计意图**：用时间线让学生看到 GPU 自身也在走向专用化（制造"SIMT 不是终点"的认知），用辩论让学生主动思考编程模型的未来，最后自然引出下节课 CANN 的多层抽象作为一种可能的答案。

## 三、第 4.2 课：NPU 架构如何应对 AI 时代大模型挑战

### 4.2 时段详细设计

#### 时段 0：回顾导入与"拆盲盒"（0:00 – 0:10，10 分钟）

**内容设计**：
1. **回顾上节课（3 分钟）**：快速回顾大模型四大特征（计算规则、访存量大且规则、计算访存可分离、控制流简单）和 CPU/GPU 的局限。

2. **"拆盲盒"导入（5 分钟）**：
   > "上节课我们说需要新的架构。这节课我们来'拆'一个昇腾 950 的架构盲盒——不看说明书，先看芯片架构图，**猜一猜每个模块是干什么的、为什么这么设计**。"
   - 展示 950 架构框图（Die 照片或架构图），标注：AI Core（Cube/Vector/Scalar）、UB、L1、L0A、L0B、L0C、HBM、NDDMA、SMMU
   - 让学生猜：L0A/L0B/L0C 可能是什么？为什么有三个 L0？NDDMA 和普通 DMA 有什么不同？
   - 不揭晓答案，带着悬念进入四个维度

3. **本课路线图（2 分钟）**：四个维度逐一拆解，每个维度都遵循"经典做法→AI挑战→CANN设计→为什么这样设计"。

---
#### 时段 1：维度一——计算单元，从通用核到专用三核异构
**内容设计**：
1. **经典做法回顾（3 分钟）**：
   - CPU：通用超标量核，什么都能算
   - GPU：SIMT 统一 SM，所有 CUDA Core 相同
   - 共同特点：**计算单元同质化**——所有核心做同样的事

2. **AI 挑战（5 分钟）**：
   - 大模型算子不是一种计算，而是三类性质完全不同的计算：
     - **矩阵乘**（GEMM/Conv）：规则的二维数据流动，需要大量 MAC（乘加）单元，数据复用率极高
     - **矢量计算**（激活/归一化/逐元素）：一维向量的逐元素操作，需要简单 ALU，访存模式规则
     - **标量控制**（循环/分支/地址计算/DMA 控制）：控制流和地址计算，需要通用标量核
   - 如果用同一种通用核做这三类计算，每类都做不到最优——矩阵乘的 MAC 利用率低，矢量计算的控制开销大，标量计算浪费向量单元

3. **CANN 设计：三核异构（12 分钟）**：
   - **Cube 单元**：
     - 专用矩阵乘阵列（脉动阵列，Systolic Array）
     - 直接硬件实现矩阵乘，不需要取指译码，数据在阵列中流动
     - 950 的 Cube 支持 FP16/BF16/INT8/INT4 等多种精度
     - **类比**：餐厅的"炒菜专岗"——专门颠勺炒菜，不做切菜和传菜
   - **Vector 单元**：
     - 矢量计算，支持 b8~b64 多种数据类型
     - 处理激活（ReLU/GELU/SiLU）、归一化（LayerNorm/RMSNorm）、逐元素运算（Add/Mul/Div）、归约（ReduceSum/ReduceMax）
     - 与矢量寄存器（VL=256B）配合，一次处理 256B 数据
     - **类比**：餐厅的"切菜/备菜专岗"——专门做切菜、洗菜、摆盘，不炒菜
   - **Scalar 单元**：
     - 标量控制，处理循环控制、条件分支、地址计算、循环变量维护
     - 控制 DMA 数据搬运、控制 Cube/Vector 的启动和同步
     - **类比**：餐厅的"传菜员/调度员"——负责下单、传菜、协调各个岗位，不直接做菜
   - **三核协同流程**（以 GEMM+bias+ReLU 为例）：
     ```
     Scalar: 控制循环，计算地址，启动 DMA 搬运 A/B 矩阵块到 UB
     DMA:    从 HBM 搬 A/B 到 UB（与计算并行）
     Scalar: 启动 Cube 做 A×B 矩阵乘，结果到 L0C
     Cube:   执行矩阵乘（脉动阵列，数据流动）
     Scalar: 启动 Vector 从 L0C 读结果，加 bias，做 ReLU
     Vector: 执行 bias add + ReLU
     Scalar: 启动 DMA 把结果从 UB 搬回 HBM
     ```
   - **关键**：三核可以**并行流水**——Scalar 控制下一次循环的 DMA 时，Cube 在算当前矩阵乘，Vector 在处理上一次的结果——三核同时忙，而不是串行等待

4. **概念测试题（Peer Instruction，5 分钟）**：
   > **问题**：在昇腾三核架构中，以下哪个工作最适合由 Scalar 单元执行？
   > - A. 两个 256×256 矩阵相乘
   > - B. 对一个向量的每个元素做 ReLU 激活
   > - C. 计算循环变量 i 的下一个地址，启动 DMA 搬运下一批数据
   > - D. 对一个向量求所有元素的和（ReduceSum）
   独立投票→同伴讨论→再投票→讲解。答案 C。A 是 Cube，B/D 是 Vector，C 是 Scalar 的控制和地址计算职责。

5. **小组讨论：体系架构如何同时支持离散访问、连续访问？（5 分钟）**：
   - **Think-Pair-Share**：
     - 独立思考（2 分钟）：引导讨论950同时支持**SIMD和SIMT**编程，以及SIMD/SIMT混合编程；

6. **回归体系结构原理（5 分钟）**：
   - **领域专用架构（DSA, Domain-Specific Architecture）**：为特定领域定制计算单元，牺牲通用性换取能效比（TOPS/W）
   - 三核异构是 DSA 的典型实现——不是一个大通用核，而是三个专用核协同
   - **历史脉络**：CPU（通用）→ GPU（半专用，SIMT+Tensor Core）→ NPU（专用，三核异构+脉动阵列），专用化程度越来越高
   - **代价**：灵活性降低——三核架构不适合跑通用程序（如操作系统、编译器），但对 AI 算子效率极高
---

#### 时段 2：维度二——存储层次，从硬件 Cache 到软件管理的 UB/L1/L0A/L0B/L0C + RegFile（0:45 – 1:20，35 分钟）

**内容设计**：

1. **经典做法回顾（3 分钟）**：
   - CPU：Reg→L1→L2→L3→主存，全部硬件管理（除了 Reg 由编译器分配）
   - GPU：Reg→Shared Memory（软件管理）→L1→L2→Global Memory，混合管理
   - 核心问题：**谁来决定数据在哪个层次、什么时候搬入搬出？** CPU 是硬件，GPU 部分是软件（Shared Memory）

2. **AI 挑战（5 分钟）**：
   - 大模型访存模式规则且编译时可知（上节课结论），硬件 Cache 的自动管理不够精准
   - 大模型数据量大，需要更精细的存储层次来支撑数据复用和计算访存重叠
   - 矩阵乘需要多个输入缓冲（A 矩阵、B 矩阵）和输出缓冲，且生命周期不同——硬件 Cache 无法感知这种算子级的数据布局

3. **CANN 设计：昇腾 950 存储层次逐层拆解（20 分钟）**：

   从远到近（离计算单元从远到近）：

   - **GM（Global Memory，全局存储）**：
     - HBM2e/HBM3，容量 32~64 GB，带宽 ~1.6 TB/s（950），延迟 ~数百周期
     - 存储模型参数、输入输出、中间结果
     - **类比**：餐厅的"中央冷库/仓库"——容量大，距离远，取菜慢，需要大卡车（DMA）批量运输

   - **L2 Cache**：
     - 硬件管理，容量 ~数 MB，用于跨核共享和不规则访存缓存
     - **类比**：餐厅的"公共食材暂存区"——多个厨房共用，硬件自动管理

   - **L1 Buffer / L1**：
     - 硬件管理或软件可控，核内私有，容量 ~数百 KB
     - 作为 UB 和 L2 之间的桥梁，也用于某些场景的数据缓存
     - **类比**：厨房门口的"收货台"——从冷库运来的菜先放这里，再分到各个操作台

   - **UB（Unified Buffer，统一缓存）**：
     - **软件管理**的 SRAM，容量 ~数百 KB~1 MB（950 每个 AI Core 有 256 KB UB）
     - **核心角色**：AI 算子的"主战场"——计算的输入数据先搬到 UB，计算的输出先写到 UB，再由 DMA 搬回 GM
     - 软件完全控制：哪些数据驻留 UB、什么时候搬入、什么时候搬出、UB 内的数据布局（ND/NZ Format）
     - **类比**：厨房的"操作台/备菜台"——厨师（计算单元）就在这里做菜，所有食材（数据）必须先放到操作台上才能用，厨师自己决定台上放什么、怎么摆

   - **L0A / L0B / L0C（Cube 的输入输出缓冲）**：
     - **软件管理**的超高速 SRAM，离 Cube 单元最近（1~2 周期）
     - **L0A**：Cube 的第一个输入矩阵（A 矩阵）缓冲
     - **L0B**：Cube 的第二个输入矩阵（B 矩阵）缓冲
     - **L0C**：Cube 的输出结果缓冲（C = A × B 的结果先存在这里）
     - 为什么要分三个？因为矩阵乘需要同时读两个输入、写一个输出，生命周期不同——A/B 读完就可以覆盖，C 写完后 Vector 才能读
     - **类比**：炒菜灶台上的"三个专用碗"——左边碗放主料（A），右边碗放配料（B），前面碗放炒好的菜（C），三个碗分工明确，不会混

   - **RegFile（矢量寄存器堆）**：
     - **软件管理**的高速寄存器，离 Vector 计算单元最近（1 周期）
     - 每个数据寄存器 VL=256B，支持 b8~b64 多种数据类型
     - 存储 Vector 单元当前正在计算的数据，也用于中间结果暂存
     - **类比**：厨师手里的"炒勺/小碗"——正在炒的菜在炒勺里，炒完倒到输出碗（L0C/UB）

   - **存储层次总图**：
     ```
     GM (HBM, 32GB, 1.6TB/s)
       ↑↓ DMA (NDDMA)
     L2 Cache (硬件管理, ~MB)
       ↑↓
     L1 Buffer (硬件/软件, ~数百KB)
       ↑↓ DataCopy (片上搬运)
     UB (软件管理, 256KB, 算子主战场)
       ↑↓ DataCopy
     L0A / L0B / L0C (软件管理, Cube 专用缓冲, 最近)
       ↑↓
     Cube (矩阵乘计算单元)
     
     UB
       ↑↓ DataCopy
     RegFile (软件管理, 256B/寄存器, Vector 专用)
       ↑↓
     Vector (矢量计算单元)
     
     Scalar (标量控制单元) → 控制所有 DMA/DataCopy/计算启动
     ```

#### 时段 3：维度三——数据搬运，如何应对多维张量传输和布局变换（对齐、大包、同地址冲突、Layout变换、NDDMA）等（1:25 – 1:55，30 分钟）

**内容设计**：

1. **经典做法回顾（3 分钟）**：
   - CPU：load/store 指令，硬件 Cache 自动管理，地址对齐由硬件处理（非对齐访问硬件自动拆分但有性能惩罚）
   - GPU：global memory load/store，Shared Memory 有 Bank Conflict 问题，cudaMemcpy 主机-设备拷贝
   - 共同特点：数据搬运通常是"一维线性"的——从地址 A 搬 N 字节到地址 B

2. **AI 挑战（5 分钟）**：
   - 大模型的数据是**多维张量**（4D/5D：NCHW/NHWC、[batch, seq, head, dim]），不是一维线性数据
   - 搬运时需要做**布局变换**（transpose、reshape、维度重排、padding）
   - 矩阵乘需要特定的数据布局（分块 tiling、NZ 格式压缩）
   - 一维 DMA 无法高效处理多维张量搬运——需要多次一维搬运+软件处理布局，效率低

3. **CANN 设计：NDDMA 与数据布局（15 分钟）**：

   - **对齐与非对齐访问**：
     - **对齐访问**：地址是 32B（或 64B/128B）的整数倍，一次搬运完成，效率最高
     - **非对齐访问**：地址不满足对齐要求，跨 32B 边界，硬件需要拆成两次访问+拼接，有性能惩罚
     - CANN 提供**非对齐寄存器**支持非对齐 load/store，硬件自动处理跨边界拼接
     - **类比**：快递分拣——对齐地址像"整箱包裹"，一次搬一箱；非对齐像"散件包裹"，需要拆箱、重新打包，多花时间

   - **ND Layout（N-Dimensional，多维布局）**：
     - 数据按原始多维张量布局存储，每个维度有独立的 stride（步长）
     - NDDMA 支持**多维地址生成**——一次 DMA 描述可以描述"从 4D 张量的 [n,c,h,w] 位置搬一个 3D 子块"，不需要软件循环多次一维 DMA
     - 支持 stride（步长）、repeat（重复）、offset（偏移）等多维参数
     - **类比**：快递分拣中的"按区域批量取件"——不是一件一件取（一维 DMA），而是按"华东区、浙江省、杭州市"的多维地址一次性取整个区域的包裹（NDDMA）

   - **NZ Layout（Non-Zero / NZ Format，压缩布局）**：
     - 针对矩阵乘优化的专用数据布局，将矩阵按分块（block）压缩存储，去除 padding 和零元素
     - 提高 Cube 单元的计算效率（不浪费 MAC 单元在零元素上）
     - 减少存储和带宽占用
     - NZ Format 通常由编译器或算子库自动转换，开发者不需要手动处理
     - **类比**：快递中的"真空压缩包装"——把包裹里的空气（零元素/padding）抽掉，减小体积，运输更高效

   - **NDDMA（N-Dimensional DMA，多维 DMA 引擎）**：
     - 昇腾专用的数据搬运引擎，支持多维张量搬运
     - 功能：GM↔UB 搬运、UB↔L0 搬运、UB 内数据复制、布局转换（ND↔NZ、transpose）
     - 由 Scalar 单元控制启动，与 Cube/Vector 计算并行（计算时同时搬下一批数据）
     - 支持异步操作和事件同步（DMA 完成后触发计算）
     - **类比**：餐厅的"智能传菜机器人"——不仅能传菜（一维搬运），还能按订单自动从不同货架取不同菜品、组合成一桌菜（多维搬运+布局变换），传菜时厨师可以继续炒菜（计算搬运并行）

   - **数据搬运的完整流程**（以 GEMM 为例）：
     ```
     1. Scalar 计算 A/B 矩阵块在 GM 中的多维地址
     2. Scalar 启动 NDDMA：从 GM 搬 A 块到 UB（ND Layout）
     3. Scalar 启动 NDDMA：从 GM 搬 B 块到 UB
     4. NDDMA 完成后，Scalar 启动 DataCopy：UB→L0A（A 矩阵）、UB→L0B（B 矩阵）
     5. Scalar 启动 Cube：A×B → L0C
     6. Cube 计算的同时，NDDMA 并行搬下一个 A/B 块到 UB 的另一区域（Double Buffer）
     7. Cube 完成后，Scalar 启动 Vector：从 L0C 读结果，后处理（bias+激活），写回 UB
     8. Scalar 启动 NDDMA：从 UB 搬结果回 GM
     ```

4. **概念测试题（Peer Instruction，4 分钟）**：
   > **问题**：在昇腾架构中，NDDMA 最核心的优势是什么？
   > - A. 比普通 DMA 搬运速度更快（带宽更高）
   > - B. 支持多维张量搬运和布局变换，减少软件循环和多次一维 DMA
   > - C. 可以直接做矩阵乘计算
   > - D. 可以替代 Cache，不需要 UB 了
   独立投票→同伴讨论→再投票→讲解。答案 B。NDDMA 的核心是"多维"和"布局感知"，不是带宽更高（带宽由 HBM 决定）。

5. **回归体系结构原理（3 分钟）**：
   - **数据搬运是存储层次的核心操作**——如何高效地在层次间移动数据
   - CPU/GPU 的一维 DMA 是为通用线性数据设计的
   - AI 负载是多维张量 → NDDMA 为多维数据定制，又是一次"专用化"
   - **计算与访存解耦**：NDDMA 独立于计算单元，由 Scalar 控制，可以与 Cube/Vector 完全并行——这是实现 Double Buffer 和计算搬运重叠的硬件基础

   - **Ascend C Tensor API（中层）**：
     - 开发者感知 Tensor（数据类型、shape、布局）和算子计算逻辑
     - 不感知 UB 地址、寄存器分配、DMA 调度——由编译器和运行时自动处理
     - 提供类库函数（如 matmul、conv、reduce、elementwise），开发者组合调用
     - 性能较好，开发门槛中等，适合大多数自定义算子开发
     - **类比**：开"自动挡家用车"——不需要手动换挡，油门刹车方向盘自己控制，有一定驾驶乐趣，适合大多数人

   - **PyPTO / PyPTO Pro（高层）**：
     - 开发者只写 Python 级别的 Tensor 运算（如 `tensor.matmul(a, b)`、`model(input)`）
     - 完全不感知硬件——编译器自动做算子融合、布局转换、VF 粒度选择、数据搬运优化
     - PyPTO Pro 提供更多优化选项（如自定义算子融合、内存规划），但仍在 Python 层面
     - 开发效率最高，性能依赖编译器优化，适合算法工程师快速验证和模型部署
     - **类比**：坐"自动驾驶出租车"——只需要说目的地，完全不需要开车，最省心，但无法控制具体驾驶方式

   - **核心设计哲学：渐进式暴露硬件能力**：

#### 时段 2：优化维度二——流水并行优化（0:55 – 1:30，35 分钟）
**内容设计**：

1. **问题：计算和搬运能同时进行吗？（5 分钟）**：
   - 上节课讲了计算和访存可静态分离（大模型算子的特征）
   - 但"可分离"不等于"自动重叠"——需要软件显式安排流水
   - 如果计算和搬运串行（搬完一批→算一批→搬下一批→算下一批），计算单元有一半时间在等数据
   - **目标**：让计算单元 100% 忙碌，搬运在后台并行进行

2. **Double Buffer（双缓冲）原理（15 分钟）**：
   - **单缓冲（Single Buffer）的问题**：
     ```
     时间线：
     t0-t1: DMA 搬数据到 UB（计算单元空闲）
     t1-t2: Cube 计算（DMA 空闲）
     t2-t3: DMA 搬下一批（计算单元空闲）
     t3-t4: Cube 计算（DMA 空闲）
     利用率：计算单元 50%，DMA 50%
     ```
     - 类比：餐厅只有一个备菜台——厨师等菜备好了才能炒，备菜时厨师闲着，炒菜时备菜台闲着
   - **双缓冲（Double Buffer）的原理**：
     - UB 分成 A/B 两块（或两组区域）
     - 计算单元用 A 块数据计算的同时，DMA 往 B 块搬下一批数据
     - 计算完 A 块后，交换角色（用 B 块计算，往 A 块搬下一批）
     ```
     时间线：
     t0-t1: DMA 搬 A 块（计算空闲）
     t1-t2: Cube 算 A 块 + DMA 搬 B 块（并行！）
     t2-t3: Cube 算 B 块 + DMA 搬下一个 A 块（并行！）
     t3-t4: Cube 算下一个 A 块 + DMA 搬下一个 B 块（并行！）
     利用率：计算单元 ~90%+（只有第一次搬运是串行的，之后全并行）
     ```
   - **现场演示**（如果有环境）：
     - 展示单缓冲 vs 双缓冲的性能对比实测（同一个 GEMM 算子，单缓冲 ~150 TFLOPS，双缓冲 ~280 TFLOPS）
     - 用 profiling 工具展示计算单元和 DMA 的时间线，直观看到单缓冲的"气泡"和双缓冲的"填满"
     - 如果没有真机环境，用预录的视频或动画演示

   - **计算与访存解耦**：Double Buffer 和三级流水的本质是让计算和访存（以及不同计算阶段）完全重叠，隐藏访存延迟
   - **流水线（Pipelining）原理**：和 CPU 的指令流水线（取指→译码→执行→访存→写回）是同一个原理——把一个任务分成多个阶段，各阶段并行执行

#### 时段 4：单芯片极限与超节点

**内容设计**：
1. **单芯片极限与超节点（SuperPod）（4 分钟）**：
   - **单芯片优化的极限**：
     - 经过四个维度的优化，单芯片（950）的 GEMM 可以跑到 90%+ 峰值
     - 但单芯片的物理极限摆在那里：
       - 算力极限：芯片面积和功耗决定了 MAC 单元数量上限（950 ~320 TFLOPS FP16）
       - 带宽极限：HBM 引脚数和功耗决定了带宽上限（950 ~1.6 TB/s）
       - 容量极限：HBM 容量上限（950 64GB），70B 模型 FP16 需要 140GB，单芯片装不下
       - 功耗极限：单芯片功耗 ~400W，散热和供电有物理上限
   - **大模型增长超过单芯片极限**：
     - 模型参数：7B→70B→175B→500B→1T+，单芯片 GM 装不下
     - 训练算力：GPT-3 训练需要 ~3.14×10^23 FLOPs，单芯片 320 TFLOPS 需要 ~31000 年（不考虑效率），必须用数万张卡并行
     - 推理延迟：大模型推理需要多卡张量并行/流水线并行才能满足延迟要求
   - **必然走向超节点（SuperPod）**：
     - 什么是超节点：将数十到数百个 AI 芯片通过高带宽互连（NVLink/PCIe/RoCE/InfiniBand）组成一个紧密耦合的计算集群，对外表现为一个"超级计算节点"
     - 典型超节点：NVIDIA DGX SuperPod（140 台 DGX，8 卡/台，共 1120 张 A100，InfiniBand 互连）；昇腾 Atlas 900 SuperPod（1024 张 950，HCCS + RoCE 互连）
     - 超节点的核心挑战：**多卡间的数据搬运和协同计算**——单芯片内的存储层次和数据搬运优化，扩展到多卡间就变成了互连网络问题
   - **自然过渡到第 5 章**：
     > "单芯片内我们用 UB/L0/RegFile 做存储层次，用 NDDMA 做数据搬运，用 Double Buffer 做计算访存重叠。到了多卡超节点，这些问题变成了：卡间用什么互连？（NoC/PCIe/CXL）数据怎么在卡间高效搬运？（RDMA）多卡怎么协同计算？（分布式并行）这就是下一章「Interconnect」要讲的内容。"
