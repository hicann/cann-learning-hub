# 参考答案

有效报告应包含唯一变量、相同矩阵和迭代配置、CPU reference、阶段时间、误差、footprint、balance ratio，以及基于构建和调用点的执行位置判断。即使性能退化，也应保留结果并解释。


## 参考实验操作

实验必须基于 `src/ascend_spmv/`。构建运行 benchmark，沿 `ISpmvBackend` 追踪各实现；比较精度、partition、cold/warm 和误差；FP32 正式路径已有 Device API（`AscendCSpmvBackend`），FP16/BF16/persistent 无 Device 调用时只报告主机原型证据。

建议记录表：

| Backend | Precision | Cold | Warm | Compression | Balance | Error |
|---|---|---|---|---|---|---|
|  |

分析时先判断退出码、正确性和可比性，再解释性能变化。若环境缺少 CANN、MPI 或多设备，应提交明确的诊断证据，不得把历史 CSV 冒充本机运行结果；参考答案不规定固定耗时。

## 四类考核参考答案

### 1. 客观题

答案：（1）B。正式运行 CSV 中 `actual_backend=ascend_c`，日志为 `Actual Backend=Ascend C RTC`。（2）`AscendCSpmvBackend`。（3）对。`ascendc_launch_to_complete_ms` 是 launch-to-complete 口径（kernel 提交到 stream 同步完成，含启动与执行），不是纯 kernel 执行时间。FP32 正式路径的 RTC 链为：`aclrtcCreateProg` → `aclrtcCompileProg` → `aclrtcGetBinDataSize`/`aclrtcGetBinData` → `aclrtBinaryLoadFromData` → `aclrtBinaryGetFunction` → `aclrtLaunchKernelWithConfig` → `aclrtSynchronizeStream`（真实类 `AscendCSpmvBackend`）。FP16/BF16/persistent 路径仍是 Host Prototype：它们没有走上述 Device RTC 链路，只在 Host 上完成数值循环，因此不能计为 NPU 结果。

### 2. 简单题

处理方法：给出运行命令与 CSV 头部及一行数据，逐字段解释：cold/warm（冷/热计时口径，warm 是同一进程内重复执行，cold 是端到端首跑）、total、compression（压缩/存储比率类字段）、balance（分区均衡）、error（相对误差）。能证明 Device 执行的字段是构建配置与日志中的 RTC 编译/加载/启动证据，而不是字段名里含 npu/device 的字样。判定条件：字段解释正确，且区分“字段名”与“运行位置证据”。

### 3. 中等题

处理方法：选择 partition 候选数或精度路径为唯一变量，同一矩阵与同一 warmup/repeat 运行修改前后版本，比较 total、balance、error。执行位置判断依据构建依赖与调用点（例如 `run()` 内是否有 RTC 编译与 `aclrtLaunchKernelWithConfig` 调用），不能只看变量名。判定条件：唯一变量成立、字段级对比完整、执行位置结论有代码/日志证据。

### 4. 困难题

处理方法：通读 `spmv_benchmark.cpp` 与脚本，列出 cold/warm 与执行位置相关字段的真实语义（哪些是原型阶段划分、哪些能证明 Device 执行）；对照历史 CSV 的来源说明（旧 Host 原型或旧实现生成）指出哪些不能作为当前 NPU 结果。设计可复核判定：例如要求日志包含 RTC 编译/加载与 kernel launch 记录，或用构建配置（真实 backend 开关）作为证据回答“这次运行在哪里计算”。判定条件：口径审计完整、历史数据被明确标注、判定步骤可在不修改仓库的前提下复核。
