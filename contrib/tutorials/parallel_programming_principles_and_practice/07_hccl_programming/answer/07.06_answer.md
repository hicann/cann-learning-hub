# 参考答案

先验证 communicator 和误差，再比较 rank。通信随 rank 增长、局部 Device SpMV 计算下降与 collective/传输开销共同决定端到端结果。


## 参考实验操作

实验必须基于 `src/hccl_spmv/`。用实际 server/device IP 运行 `generate_rank_table.py`（仅接受 `--server-ip`/`--device-ip`/`--output`，`device_id`/`rank_id` 按地址顺序自动生成），strict real 模式构建后用 `run.sh`/`run_scaling.sh` 改 Rank 数；2/4 rank 分别使用各自匹配的 rank table（`rank_table_2p.json`/`rank_table_4p.json`），不要用一个 4-rank JSON 配合 `--npus-list 2,4`，也可不传 rank table 走单机 root-info fallback；检查 `rank_*.log`。`run.sh` 聚合输出按 rank 顺序带 `===== rank N =====` 标题回放每个 rank 的完整日志，每个 case 日志保留全部 rank 证据。合格日志必须同时显示 `Actual Compute Backend=Ascend C FP32 RTC` 与 `Communication Backend=ACL+HCCL`。

建议记录表：

| Ranks | HCCL | Transfer | Local SpMV | Total | Error | 日志 |
|---|---|---|---|---|---|---|
|  |

分析时先判断退出码、正确性和可比性，再解释性能变化。若环境缺少 CANN、MPI 或多设备，应提交明确的诊断证据，不得把历史 CSV 冒充本机运行结果；参考答案不规定固定耗时。

## 四类考核参考答案

### 1. 客观题

答案：（1）A。`generate_rank_table.py` 只接受 `--server-ip`、`--device-ip`（1–8 个，按设备顺序）与 `--output`，没有 `--device-id`/`--rank-id` 参数。（2）对。`device_id` 与 `rank_id` 按 `--device-ip` 的地址顺序自动生成（0..N-1），重复 `device_ip` 会被校验拒绝；2 rank 与 4 rank 必须分别使用各自匹配的 rank table（`rank_table_2p.json`/`rank_table_4p.json`），不能用一个 4-rank JSON 配合 `--npus-list 2,4`，也可不传 rank table 走单机 root-info fallback。验证：两个 rank 的 `device_id` 互不相同，且与 `rank_*.log`/`npu-smi` 显示的 device 一致。

### 2. 简单题

处理方法：给出 2 rank 运行命令与输出中的 `Actual Compute Backend=Ascend C FP32 RTC`、`Communication Backend=ACL+HCCL`、`Correctness=PASS`、`CPU Reference Error`，以及 `Local SpMV launch-to-complete` 字段值。该字段 = 本地 Ascend C SpMV 从 kernel launch 提交到 stream 同步完成的时间（launch overhead + 等待），不是 Host 计算时间。汇总耗时由 rank 0 使用 `HcclAllReduce(MAX)` 跨 rank 聚合（关键路径 wall time，字段带 `(MAX)` 后缀），每 rank 还有 `Local ...` 本地摘要。判定条件：后端与正确性字段齐全，计时边界解释正确。

### 3. 中等题

处理方法：数据流为 rank 0 的 Device `x` 经 HCCL Broadcast 分发到各 rank Device buffer → 各 rank 用本地 CSR 分片执行 Ascend C RTC SpMV（计入 `local_spmv_launch_to_complete_ms`）→ 本地 `y` 经 HCCL AllGather 汇总；每次 solve 固定 1 次 Broadcast + 1 次 AllGather（另含同步）。证据字段：HCCL Communication、Data Transfer、Synchronization、local SpMV 与 total。判定条件：数据流描述正确、collective 次数与字段对应、数值来自本次运行输出。

### 4. 困难题

处理方法：用 2 与 4 rank 的实测结果把 total 分解为 collective、transfer、本地 SpMV、同步；计算每 rank 通信量（向量长度 × 次数）与并行效率 E=Speedup/N，说明最优 rank 数由“分片收益能否摊薄 collective 固定延迟”决定。失败场景示例：rank table 中两个 device 使用同一 `device_ip`（或 device_id 重复），预期生成/运行阶段报错；用 `rank_*.log` 与退出码定位失败发生在生成、初始化还是 collective 阶段。判定条件：分解与效率计算有字段依据、失败场景可复现并给出日志定位方法。
