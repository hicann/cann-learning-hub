# 参考答案

实践必须引用源码真实 API，确认构建日志不是 stub，并保留误差阈值。参数变化只影响 shape/nnz 等一个维度。


## 参考实验操作

实验必须基于 `src/acl_operator_calls/`。分别进入 `GEMM-acl`、`SpMV-acl` 执行 build/run；先确认输出是 real 还是 stub，再沿 `main.cpp` 标出创建、执行、同步、验证和释放位置。

分析时先判断退出码、正确性和可比性，再解释性能变化。若环境缺少 CANN、MPI 或多设备，应提交明确的诊断证据，不得把历史 CSV 冒充本机运行结果；参考答案不规定固定耗时。

## 四类考核参考答案

### 1. 客观题

答案：（1）B。`SpMV-acl/src/main.cpp` 直接调用 `aclsparseSpMV(handle, ACL_SPARSE_OP_NON_TRANSPOSE, &alpha, matrix, vec_x, &beta, vec_y, ACL_FLOAT, ACL_SPARSE_SPMV_ALG_DEFAULT, nullptr)` 执行，不查询、不分配 workspace（输出 `Workspace bytes=0 (API default workspace)`），也没有手动写入 CSR 数据或稠密 SpMM 路径；workspace 查询、`aclrtMalloc` 分配与 executor 只属于 GEMM 的 `aclnnGemmGetWorkspaceSize` 链。（2）对。handle、matrix、vec_x、vec_y 与 GEMM workspace 均使用最小 RAII scope guard（`SparseDescriptors`/`Workspace`）管理：析构顺序与创建顺序相反（vec_x、vec_y → matrix → handle），且析构不抛异常——任何一步创建或执行失败抛错时，已成功创建的资源仍按该顺序全部释放，不会直接退出泄漏资源。

### 2. 简单题

处理方法：给出构建日志中 `ACL_C_STUB:BOOL=OFF`（或 CMake 打印的 real backend）行、运行命令（如 `bash SpMV-acl/scripts/run.sh --rows ... --nnz ... --repeat 10`）、程序退出码，以及输出中的相对误差与 `1e-6` 门槛比较。判定条件：四部分证据齐全，且结论明确为真实 ACL 后端。

### 3. 中等题

处理方法：SpMV 运行输出只有 Actual Backend、Device ID、Workspace bytes、Timing scope、rows/cols/nnz、ACL SpMV time、CPU Reference Error、Correctness，没有独立的 H2D/D2H 计时分项；H2D/D2H 位置在源码中（`copy_to_device`/`copy_to_host`）。分别运行 GEMM 与 SpMV，在各自固定输入下核验真实调用链、同步、时间字段、误差和 workspace 语义（GEMM 有 workspace/executor；SpMV 直接 `aclsparseSpMV(..., nullptr)`，输出没有独立 H2D/D2H 计时分项）。GEMM 与 SpMV 是不同数学运算、不同输入表示，不能把两者耗时当作可比性能结论；对比的是 API/资源生命周期与证据字段。证据字段：规模、Backend、Workspace bytes、ACL SpMV time、CPU Reference Error。判定条件：题目按“分别固定输入核验调用链与证据字段、不跨 API 比较耗时”的语义作答，结论引用实测字段并说明 dense/sparse 存储与计算模式差异。

### 4. 困难题

处理方法：构造一个错误场景（例如跳过资源初始化直接执行，或跳过同步直接取结果，或重复释放同一资源），记录 ACL 错误码与日志所在层次，说明该错误发生在资源生命周期的哪一步以及正确清理顺序。后端证明不能靠变量名：必须引用运行时输出（构建日志中的 real backend、设备上执行的 API 返回值、误差通过 `1e-6` 门槛）说明计算发生在真实 NPU。判定条件：错误可复现、错误码/日志被引用、清理要求正确、后端证据来自运行时而非命名。
