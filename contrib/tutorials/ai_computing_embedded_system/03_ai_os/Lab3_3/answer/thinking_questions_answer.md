## 思考题 1：为什么部署昇腾环境必须遵循"固件→驱动→CANN"的顺序？如果顺序颠倒会发生什么？

**参考答案**：

昇腾环境的三层组件存在**自下而上的层层依赖**关系：

- **固件**烧录在 NPU 芯片内部，是最底层的硬件控制代码，无需安装；
- **驱动**运行在操作系统内核中，负责让 OS 识别并管理 NPU 设备，依赖固件提供的硬件接口；
- **CANN** 运行在用户态，通过调用驱动提供的设备接口来调度 NPU 资源，依赖驱动正确安装。

如果顺序颠倒（如先装 CANN 再装驱动）：

1. CANN 安装脚本会检测 NPU 设备节点（如 `/dev/davinci0`），若驱动未安装则设备节点不存在，CANN 安装会报"找不到 NPU 设备"错误；
2. 即使强制安装成功，CANN 运行时调用 `aclrtSetDevice()` 也会失败，因为驱动未加载，OS 无法将任务下发到 NPU；
3. 环境变量配置不完整，`LD_LIBRARY_PATH` 中缺少驱动相关的库路径。

因此必须严格遵循"固件→驱动→CANN"的顺序，先确保硬件被 OS 正确识别，再搭建上层软件环境。

## 思考题 2：CANN 的四层软件栈中，哪一层是开发者最常接触的？为什么？

**参考答案**：

开发者最常接触的是 **👑 应用开发与编程接口层**（AscendCL、GE、ATC）。

原因如下：

| 模块 | 开发者接触频率 | 原因 |
|---|---|---|
| **AscendCL** | ⭐⭐⭐⭐⭐ | 开发 AI 应用时直接调用其设备管理、内存管理、模型执行等 API |
| **ATC** | ⭐⭐⭐⭐ | 模型部署阶段必须使用，将 ONNX/框架模型转为 .om 离线模型 |
| **GE** | ⭐⭐ | 框架适配层自动调用，开发者通常不直接操作 |
| **AOL/AOE/TBE** | ⭐⭐ | 使用内置算子时自动调用，仅自定义算子时直接接触 |
| **Runtime/HCCL** | ⭐⭐ | 通过 AscendCL 间接调用，分布式训练时直接使用 HCCL |
| **HAL/SVM/HDC** | ⭐ | 完全在底层自动工作，开发者几乎不感知 |

其余三层（计算服务与编译优化层、运行时与执行层、基础与硬件抽象层）主要在内部自动协作，开发者通过 AscendCL 间接使用它们的能力。

## 思考题 3：AscendCL 与 ATC 各自承担什么角色？分别适合什么场景？

**参考答案**：

| 对比项 | AscendCL | ATC |
|---|---|---|
| **角色** | 运行时编程接口 | 编译时模型转换工具 |
| **功能** | 设备管理、内存管理、模型加载与执行、算子加载与执行 | 将 ONNX/框架模型编译优化为 .om 离线模型 |
| **使用阶段** | 运行时（推理/计算） | 部署前（编译/转换） |
| **典型场景** | 开发 AI 推理应用，加载 .om 模型并执行推理 | 将训练好的 PyTorch/ONNX 模型转为昇腾专用 .om 格式 |
| **类比** | CUDA Runtime API | nvcc 编译器 |

**典型工作流**：

```
训练框架(PyTorch) → 导出 ONNX → [ATC 编译] → .om 离线模型 → [AscendCL 加载执行] → 推理结果
```

- **ATC 适合的场景**：模型部署前，需要将框架模型转为昇腾硬件最优的 .om 格式，进行图优化和算子融合。
- **AscendCL 适合的场景**：运行时加载 .om 模型，管理 NPU 设备和内存，执行推理并获取结果。

## 思考题 4：HAL（硬件抽象层）在 CANN 软件栈中起什么作用？

**参考答案**：

HAL（Hardware Abstraction Layer，硬件抽象层）是 CANN 软件栈中最底层的模块，其核心作用是**屏蔽底层硬件差异，向上层提供统一的驱动接口**。

**具体作用**：

1. **屏蔽芯片型号差异**：不同型号的昇腾芯片（如 310B4、910B3、910P3）在 AI Core 架构、核数、指令集上存在差异，HAL 将这些差异封装在内部，向上层呈现统一接口；
2. **实现代码跨芯片复用**：同一套 AscendCL 代码可以在不同型号昇腾芯片上运行，无需为每种芯片重写代码；
3. **简化上层开发**：AscendCL、Runtime 等上层模块无需关心具体硬件细节，只需调用 HAL 提供的统一接口；
4. **支持硬件演进**：新一代芯片发布时，只需更新 HAL 层实现，上层软件栈无需改动。

**架构示意**：

```
AscendCL / Runtime / HCCL  ← 上层模块调用统一接口
        ↑
      HAL  ← 屏蔽硬件差异，提供统一接口
        ↑
   ┌────┴────┬─────────┐
  310B4    910B3     910P3  ← 不同型号芯片
```

正是因为 HAL 的存在，开发者在本实验云沙箱（910B3）上编写的代码，可以几乎不加修改地移植到香橙派（310B4）上运行——只需在编译时指定正确的芯片型号（如 `Ascend310B4`）。
