# 实验报告参考要点

本文件对应《实验3.1_嵌入式驱动开发实验手册》第四部分“针对性问题探究”的参考答案要点，供实验报告撰写参考。

## 问题1：为什么 SPI 回环测试要作为外设驱动开发的第一步？它需要 wiringOP 吗？

**不需要 wiringOP。** 任务一用的是系统自带的 `spidev_test`，它直接操作内核 spidev 字符设备 `/dev/spidev0.0`，零依赖。

把它放第一步的原因是**分层验证**：用最少依赖把问题域压到最小，先确认“SPI0 控制器 + 引脚复用 + 设备节点”三层贯通。若跳过此步直接装库写程序接外设，一旦通讯失败将无法区分故障在主控侧、库、程序还是外设侧，排查成本成倍增加。

注意区分两个回环：任务一的 `spidev_test`（系统工具，零依赖）和任务三的 `spi_loopback.c`（自写程序，依赖 wiringOP）——目标都是验 SPI0 信道，但所处层级不同。

## 问题2：wiringOP 与 libgpiod 有何区别？本实验如何选择？

- **wiringOP**：将寄存器操作封装为直观的库函数（`digitalWrite`、`wiringPiSPISetupMode` 等），接口简单、与 wiringPi 生态兼容，适合快速原型开发；
- **libgpiod**：基于内核 GPIO 字符设备（`/dev/gpiochipN`），是 Linux 官方推荐的标准接口，可移植性与长期维护性更好。

本实验需要成熟的 SPI 硬件封装与快速的寄存器级时序控制，故选用 wiringOP；若做需要跨平台部署的产品化驱动，则建议迁移到 libgpiod。

## 问题3：手册用 GPIO7_02 演示，程序却控制 GPIO7_05，后者没单独配置 wiringOP 吗？

这是两层不同的“配置”，不要混淆：

| 层级 | 做什么 | 在哪做 |
|---|---|---|
| 库级安装 | 把 wiringOP 装进系统，所有引脚都可用 | 任务二 `./build install`（一次性） |
| 引脚级配置 | 把某个引脚设为输入/输出方向 | 任务三程序里 `pinMode()`（运行时） |

- 手册的 `gpio mode 2 out`（引脚7 / GPIO7_02 / wPi 2）只是 CLI 用法教学示例；
- 本实验控制引脚 40 = GPIO7_05 = wPi 25（源码 `pinToGpio_AIPRO[25]=229=7*32+5`）；
- `wiringPiSetup()` 只初始化库（建映射、开寄存器），**不设任何引脚方向**；
- `pinMode(25, OUTPUT)` 才是真正配置 GPIO7_05 的那一步，在运行时完成，等价于 `gpio mode 25 out`，**所以不需要再单独跑命令行配置**。

## 问题3：为什么 GPIO 翻转实测频率低于理论值？

`digitalWrite` 本身需要执行用户态→内核态的寄存器映射指令，存在数微秒的函数调用耗时，叠加 `delayMicroseconds` 的定时精度限制，导致实测频率（约 45~48kHz）略低于理论值（50kHz）。通过 `SCHED_FIFO` 实时调度与 `nice=-20` 提升优先级可减少调度抖动，使周期更稳定。

## 问题4：若将 SPI 时钟大幅降低做成 LED 闪烁，它与手柄通讯在驱动层面有何共性？

二者的底层机制完全相同——都是对 GPIO/SPI 引脚电平时序的编程控制：手柄通讯是“按时钟读电平”，LED 闪烁是“按周期写电平”。区别只在方向与速率。`gpio_toggle.c` 通过命令行参数切换半周期，即可在“高速翻转”与“LED 慢闪”之间复用同一套驱动代码，这正是寄存器映射类驱动库（wiringOP/libgpiod）的价值所在。
