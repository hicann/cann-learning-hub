# AscendCL 应用开发（第七章）

## 课程简介

第六章解决的是"如何把一个算子写到昇腾上去"，本章解决的是"如何把一个应用跑起来、跑得快、并说清楚时间花在哪里"。理论部分讲授 AscendCL 的应用框架与运行时资源模型（Device / Context / Stream 四级抽象、资源配对释放）、三类内存与数据传输机制、Stream 与任务级并行、Event 与设备侧计时、aclnn 两段式单算子接口，以及从 ATC 到 aclmdl 的模型推理链路。

配套实验共 7 个：应用框架实验建立七步流程与资源生命周期的骨架，且不做任何性能测量——环境规格查询、资源配对自检与错误码定位这三件事，是任何性能测量能够得出可信结论的前提；内存实验建立锁页内存与传输带宽模型；Stream 实验用多流构造传输与计算的重叠流水；Event 实验解决"主机侧计时为什么失真"并给出设备侧计时与跨流依赖的正确做法；aclnn 实验掌握两段式接口与 workspace 管理；模型推理实验走通 ATC 转换与 aclmdl 加载执行。

最后的综合实训把一个**真实的 YOLOv13 检测模型**从 PyTorch 权重完整部署为可运行的 AscendCL 推理程序，链路固定为四步：权重导出 ONNX → ATC 转出 `.om` → 编写 AscendCL 应用 → 编译运行并核对结果。在最后一步上实现两个版本：v1 由主机 CPU 完成转 FLOAT、除以 255、HWC 换 CHW 三步预处理，v2 把这三步交给静态 AIPP 在模型内部完成。

## 适合人群与前置要求

面向已完成第六章 Ascend C 学习的学习者——理解了核函数与异步下发，才能理解本章的 Stream 语义与同步管理。要求具备 C/C++ 基础；综合实训还需要基本的 Python 与深度学习模型使用经验。

## 学习目标

- 掌握 AscendCL 初始化—资源申请—释放的标准框架，能够正确管理 Device、Context 与 Stream 的生命周期；
- 能够区分并正确使用普通内存、页锁定内存与设备内存，实测并解释 H2D / D2H 传输带宽曲线；
- 能够用多 Stream 构造拷贝-计算-拷贝重叠流水，估算并验证流水线加速比上界；
- 能够用 Event 完成设备侧计时与跨流依赖构造，说明主机侧计时在异步下发场景中的失真原因；
- 掌握 aclnn 两段式接口的调用规范，正确管理 workspace 与 executor 生命周期；
- 能够用 ATC 完成模型转换，用 aclmdl 完成离线模型加载与推理；
- 能够完成检测模型的端到端部署，把时延拆解为预处理、推理、后处理三段并定位优化空间；
- 能够用静态 AIPP 把预处理从 Host CPU 转移到 Device，并定量说明收益与代价。

## 实验环境说明

- 运行前请确认：`npu-smi info` 能查到设备，`$ASCEND_TOOLKIT_HOME` 已设置；实验六、七还需 `which atc` 有输出。
- **若环境检查未通过**：先重新运行 Notebook 中的环境准备单元格；仍不通过则在终端执行 `source $ASCEND_TOOLKIT_HOME/set_env.sh` 并重启内核。
- 所有源码通过 `%%writefile` 内嵌在 Notebook 中，请自上而下依次执行各单元格（Shift+Enter）。
- **实验一不做性能测量**，其目的是把环境规格查询、资源配对自检与错误码定位这三件前提工作做扎实；性能测量从实验二开始。
- **主机侧计时在异步下发场景中会失真**：实验三之后的所有耗时数据均应以 Event 设备侧计时为准，这一点在实验四中专门讨论。
- 实验七需要联网下载 YOLOv13 权重与依赖包，并会在本地生成 ONNX 与 `.om` 文件；离线环境下请提前准备好权重与转换产物。
- ATC 转换耗时较长（分钟级），属正常现象；转换参数一旦改变需重新转换。
- 参考耗时与带宽会随芯片型号、CANN 版本、PCIe 规格与系统负载变化，学习时应关注三段时延的**构成比例**及其变化趋势。
- 遇到 🔧 **动手练习** 与 🤔 **思考题** 时，建议先独立完成，再阅读后续内容。
- 在线体验链接由仓库维护人员配置，当前记为 `-`。
