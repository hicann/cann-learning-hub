# 7.3 练习解析

本节评价的是能否沿着同一项交付目标阅读产物、判断证据并决定下一步。只复述文件名或写一句“全部通过”，不足以说明掌握了方法。

## 1. 设计怎样影响后面的工作

每行独立计算允许初始方案采用一行一任务。这项选择要落实到输入行索引、每行自己的 max/sum 和对应输出行的写回。测试还要用多行、不同数据检查各行没有混用统计量。

调优可以改变任务粒度和计算组织，但不得改变逐行 Softmax 的计算语义。

## 2. 常数输入怎样形成可信测试

一行有 N 个相等输入，减去最大值后都为 0，指数均为 1，所以每个输出为 1/N。本轮测试先用该关系核对独立参考，再调用实际 NPU 实现，并对全部元素执行既定容差比较。

输入模式、预期和断言有明确对应，真实记录说明检查实际执行。只比较 shape 无法证明数值正确；常数行也不能单独证明各行索引正确，仍需要其他适用输入补充。

## 3. ST 为什么返回修复

首次失败是编译接口对浮点 shape 没有按约定拒绝：合法参数先形成缓存后，浮点参数可能直接命中缓存，绕过内部类型检查。Agent 将检查移到缓存查询之前，再复跑相关案例和完整测试。

这次修复针对接口行为，不是 Softmax 数学公式。核对时要确认原来的参考、容差和输入要求没有放宽，并确认生成 kernel 没有因接口检查修复而改变。

## 4. 为什么用整次 kernel duration 验收

交付目标关心一次完整 kernel 调用需要等待多久，因此用设备侧 `Task Duration` 直接比较 C4 与 B0。九个案例使用相同输入、采样次数和统计方法，逐项计算耗时比，再用几何均值判断整体目标是否达到。

C4 相对 B0 的九项 kernel duration 几何均值为 0.93322，低于 0.95；最差单项为 1.00792，低于 1.05。再结合完整 ST 通过和同口径采样，本次性能目标可以判为通过。这个结论表示达到约定门槛，不表示 C4 是所有实现中的全局最优。

## 5. 课后完整流程作业怎样评分

| 项目 | 权重 | 看什么 |
|---|---:|---|
| 需求与设计 | 25% | 算子要求完整，设计的关键选择有依据，能解释它如何落实到实现 |
| 测试与反馈 | 30% | 预期可靠、断言有效、覆盖适用，实际失败与修正如实记录 |
| 候选与测量 | 30% | 候选来源清楚，全部目标案例同口径比较，主指标与交付目标一致 |
| 交付结论 | 15% | 证据对应最终版本，结论和未完成项准确，知道下一步做什么 |

允许与课程不同的实现路线和结果。性能未达标时可以提交有依据的分析，但不能将目标未满足写成完整交付通过。没有运行则不填写测试通过次数、具体耗时或提速数字。
