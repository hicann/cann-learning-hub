第 6 册《协作上库与边界》练习答案

1.（单选题）B
   解析：写后必回查（红线⑤）。PATCH/POST 返回 200 只
   说明服务器受理了请求，不代表内容按预期写入——必须
   GET 该资源核对内容。本课程 PR #1072 的回查还发现
   单查接口的状态枚举（open）与创建响应（opened）不同，
   说明成功响应的每个字段都要逐项核对。

2.（单选题）A
   解析：红线①「内容必须来源于代码」。PR 是从 diff 推导
   的交付凭证——臆造的功能声明会误导评审决策与后续的
   git blame/追溯。这条红线划出的是协作自动化的适用
   边界：推导（有据）可以，创作（无据）不行。

3.（单选题）B
   解析：边界框架的核心——按任务属性（规则明确性/
   可验证性/责任归属）分配，不按难度或成本。A/D 把
   「不重要/省钱」当依据；C 错在 Agent 产出同样必须独立
   验收（第 4 册 golden 拦下人的手算错误即是反例——
   独立参考防的不只是 Agent）。

4.（编程实践·必做）参考要点
   - 全程在自己 fork 上操作（红线③：确认目标仓归属）；
   - Issue 与 PR 的创建响应（number/iid + html_url）与
     GET 回查输出成对提交；
   - 双向关联证据：PR 描述中的「关联的Issue: #N」+
     Issue 侧的 PR 回链；
   - 加分项：commit message 遵循约定式提交；写操作前
     留一次内容预览确认的记录。

5.（编程实践·选做）参考要点
   - 重生成的标题类型（feat/fix/docs/perf）由 diff 推导，
     描述的每个模板字段都要有代码依据；
   - 「内容必须来源于代码」的体现：原 PR 描述里 diff 中
     不存在的功能声明，重生成后应当消失；
   - 写回纪律：预览确认 → PATCH → GET 回查逐项一致；
     pr-handler 不创建 Issue（边界），关联缺失需另行
     用 issue 流程补齐。
