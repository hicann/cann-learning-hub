1. 答案：B

判断依据：

- A 错误：空 Shape ReLU 案例表明，能力较弱的模型会写出不合规代码；即便模型能力较强，编码验证不分、流程跳步等问题也具有隐蔽性，并非模型自身能够完全避免。能力越强可靠性越高，但不能替代工程机制。
- B 正确：模型仍可能犯错，且这些错误大多不报错、难发现。智能体分工、独立验证、Lint Gate、状态持久化与真实 NPU 验收共同构成了工程保障：发现缺陷、拦截违规、留存证据，从而抬高交付结果的底线。
- C 错误：这些设计不替代模型编写代码，Kernel 仍由模型（Coder 智能体）实现；设计的作用是约束与验证，而非生成。
- D 错误：分工协作还会带来额外的调度与记录开销，其目标是结果可信，而非生成速度。

---

2. 答案：C

判断依据：

- A 错误：智能体分工解决的是"信息过载、关键约束遗漏"问题，将长流程拆解为多个各管一段的智能体。
- B 错误：Lint Gate 解决的是"步骤被静默跳过"问题，通过自动规则检查拦截违规代码。
- C 正确：独立验证通过让编写实现与结果校验由不同智能体承担，从机制上避免"自己写、自己判"，直接解决了编码与验证不分的问题。
- D 错误：状态持久化解决的是"中断后难以恢复"问题，将进度和决策依据持久化保存。

---

3. 答案：A、B、C、D

判断依据：

- A 正确：单一智能体需要同时承载全部开发知识与流程，极易遗忘需求、跳过规范或忽略关键约束。
- B 正确：如果同一个模型既是实现的编写者，又是与 golden 比对的校验者，验证结果无法完全采信。
- C 正确：若没有独立机制校验每一步的产出，流程可能被悄悄简化、规范可能被无意绕过。
- D 正确：若没有结构化的进度记录，一次执行失败可能污染后续环节，任务中断后无法从断点继续。
- E 错误：模型生成的代码运行速度不是"仅依靠单条 Prompt 开发算子"的隐蔽问题，这是性能优化范畴，与本章讨论的工程可靠性问题无关。

---

4. 答案：工程机制（工程保障 / 工程约束体系）

判断依据：

- 四类隐蔽问题的共同特征是"不报错、不易察觉"，单靠更强的模型无法根治，因为模型的错误性质不变。
- 需要一套围绕模型的工程机制来发现缺陷、拦截违规、留存证据，即 PyPTO Agent 的智能体分工、独立验证、Lint Gate、状态持久化与真实 NPU 验收等设计。

---

5. 答案：Lint Gate（自动门禁）；独立验证

判断依据：

- Lint Gate 在写入关键文件时自动执行规则检查，违规代码直接被拦截，对应解决"步骤被静默跳过"。
- 独立验证让编写实现与结果判定由不同智能体承担，避免"自己写、自己判"，对应解决"编码与验证不分"。

---

6. 答案：C

判断依据：

- A 错误：ReLU 算子本身非常简单（`y = max(x, 0)`），问题不在于算子难度。
- B 错误：案例强调的是"能力较弱的模型也曾生成"，但更重要的是即使模型能力较强，这类问题仍然可能发生。
- C 正确：空 Shape ReLU 案例的核心教训是，即使模型能力较强，也可能写出不合规但肉眼难以识别的代码（粗看与正常代码差异不大），需要工程机制（如 Lint Gate）来在写入阶段拦截。
- D 错误：问题不在于 PyPTO 框架的 API 设计，而在于模型可能生成不符合规范的代码。
