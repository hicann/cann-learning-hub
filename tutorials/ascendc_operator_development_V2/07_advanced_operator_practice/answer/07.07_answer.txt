07.07 参考答案

============================================================
一、五个任务的参考性能数据
============================================================

Ascend 950 环境、64物理核，msopprof Task Duration（多次采集；相邻版本
差距在10%以内时给出区间）：

| 任务 | 编程模式 | 核函数                            | Task Duration(μs) | 本步收益 |
| ---- | -------- | --------------------------------- | ----------------- | -------- |
| 任务1 | SIMT     | maxpool_gm_naive_custom           | 13.00             | —        |
| 任务2 | SIMT     | maxpool_gm_core_limited_custom    | 14.04             | 负收益   |
| 任务3 | SIMT     | maxpool_gm_warp_shfl_custom       | 7.7 ~ 8.0         | 约 45%   |
| 任务4 | 混合     | maxpool_simd_simt_ub_custom       | 7.7 ~ 8.9         | 基本持平 |
| 任务5 | 混合     | maxpool_simd_simt_ub_db_custom    | 6.85              | 约 15%   |

流水分项数据（msopprof PipeUtilization，64个block取均值）。这份数据比单次
Task Duration稳定得多，是分析收益来源的主要依据：

| 任务 | aiv_vec_time | aiv_scalar_time | aiv_mte2_time | aiv_mte3_time | aiv_total_cycles |
| ---- | ------------ | --------------- | ------------- | ------------- | ---------------- |
| 任务2 | 6.993        | 0.412           | 0.004         | 0.001         | 12239            |
| 任务3 | 3.543        | 0.405           | 0.004         | 0.001         | 6533             |
| 任务4 | 1.188        | 0.483           | 2.563         | 0.409         | 7254             |
| 任务5 | 1.093        | 0.517           | 2.610         | 0.405         | 6433             |

三条线索：
- 任务2 → 任务3：aiv_vec_time 腰斩，aiv_mte2_time 仍接近0。GM访问全部由
  vector流水发起，优化的是每条读指令的访存事务数。
- 任务3 → 任务4：aiv_vec_time 再降66%，但 aiv_mte2_time 从0涨到2.56μs。
  GM访问的开销没有消失，只是从vector流水转移到了MTE2流水。
- 任务4 → 任务5：三段流水各自耗时几乎没变，总cycle数从7254降到6433。
  收益纯粹来自重叠。

注意：绝对值会受设备状态、驱动版本影响，你的环境上可能不同，但相对趋势
应当一致。

二、分析报告参考答案
============================================================

【问题1】任务2相对任务1限制了Thread Block数，为什么在MaxPool上几乎没有
收益？如果把输入规模扩大到 8192 x 8192，收益会变大还是变小？

原因在于两个算子的任务规模量级不同。限制Thread Block数所消除的是"Block
超发带来的调度排队开销"，这项开销要在总耗时中占到可观比例，优化才有意义。
MaxPool读4MB、只写256KB，每16个输入元素才产出1个输出，整体耗时只有十几μs；
而07.05节的Transpose优化前是57μs，大一个数量级。在十几μs的量级下，超发
4倍（256/64）的排队开销相对访存耗时可以忽略，所以收益归零。

扩大到 8192 x 8192 时，收益会变得更小甚至完全消失。规模扩大后单个Block的
工作量大幅增加，总耗时上升到毫秒量级，调度开销的占比进一步被稀释。真正的
判断依据不是输入规模的绝对大小，而是"调度开销 / 总耗时"这个比值——规模越大，
这个比值越小。

需要补充的是：任务2虽然本身是负收益，但它引入的 grid-stride 循环结构是
任务4/5的必要前提。UB装不下全部256个band的数据，每个Thread Block必须在
多轮迭代间复用有限的UB缓冲区，这正是建立在"核内多轮循环"这个结构上的。
有些改动的价值不在自身的性能数字，而在于它解锁了后面的优化空间。

【问题2】任务3为什么选 asc_shfl_down 而不是 asc_reduce_max？

根本原因是本算子的规约宽度（16，一个 4x4 窗口的元素数）与 warpSize（32）
不匹配，而这两个接口对"分组"的支持完全不同。

asc_reduce_max(val) 没有 width 参数，语义是"对warp内所有活跃lane规约成
1个值"。一个warp有32条lane，正好横跨两个窗口。要让这两个窗口互不干扰，
只能让它们走不同的分支，靠线程分叉把活跃掩码分成两半——如果32条lane同时
活跃，一次 asc_reduce_max 会把相邻两个窗口的元素混在一起，算出错误结果
（实测直接导致校验失败）。

而线程分叉在SIMT硬件上是串行执行的：两个半warp不是并行规约，而是先执行
一半、再执行另一半。这就是它的代价。实测两种 asc_reduce_max 实现：
  - 实现A：整warp规约、lane16~31填 -inf，一个warp产出1个输出 → 21.96μs
  - 实现B：一线程一输入元素、两个半warp各自规约、warp零空转 → 20.72μs
实现B把lane利用率从50%提到了100%，却只快了约6%，远不是"利用率翻倍"应有的
接近2倍。这正是分叉串行执行的直接证据（aiv_vec_time 8.712 → 8.265μs）。

asc_shfl_down(val, delta, width) 的 width 参数是硬件层面的分组，不是分叉：
取 width=4 让8个分组在同一条指令里并行完成各自的规约，全部32条lane同时
活跃且互不干扰。这才是本算子需要的语义。

反过来说，如果规约宽度正好等于 warpSize（比如对一整行32个元素求最大值），
或者场景是"整warp协同产出1个结果"（softmax里对一行求max、向量点积求和），
asc_reduce_max 就非常合适——一条指令完成32路规约，比手写5步shfl树简洁。

结论：判据是"规约宽度能否和warpSize对齐、要不要分组"，而不是接口名字看
起来有多贴切。接口"能用"不等于"该用"。

（附带一个编译期细节：结构相同的 if/else 分支体会被编译器合并，因此想
"强制分叉"必须写成结构上不同的两份循环代码，否则32条lane仍然全部活跃、
结果错误。）

【问题3】任务5的双缓冲带来约15%的收益，而三段流水各自的耗时几乎完全没变。
收益是怎么产生的？为什么幅度不更大？

收益来自流水线重叠，而不是让任何一段变快。这一点在数据上非常清楚：任务4
到任务5，aiv_vec_time（1.188 → 1.093）、aiv_mte2_time（2.563 → 2.610）、
aiv_mte3_time（0.409 → 0.405）三项基本不动——搬运的数据量、规约的计算量
一个字节都没变。变化的只有总cycle数：7254 → 6433。

机制是这样的：任务4只有一组缓冲区，MTE2搬入、SIMT VF规约、MTE3搬出被锁
强制串行，总耗时约等于三段之和。任务5用两组缓冲区 + 两组独立的mutex轮换，
当前迭代的MTE2搬入使用一组缓冲区时，上一轮的VF规约和MTE3搬出可以在另一组
缓冲区上并行执行。理想情况下总耗时趋近于最长的一段而不是三段之和。

用不同的mutex是关键。如果两组缓冲区共用一个mutex，锁本身就会把它们重新
串行化，双缓冲的结构就白搭了。

收益幅度受限于三段严重不均衡：
  - MTE2 搬入 4 * 1024 * 2 个 float = 32KB，耗时 2.61μs
  - MTE3 搬出 256 * 2 个 float = 2KB，耗时 0.41μs（数据量差16倍）
  - VF 规约 1.09μs
完美重叠的下界约等于最长的一段（MTE2 的 2.61μs）加上无法重叠的固定开销。
能被重叠掉的是VF和MTE3那 1.5μs，相对总耗时本来就不大，所以只有15%。

一般规律：双缓冲的收益来自"把串行的N段压缩到接近其中最长的一段"，因此
三段耗时越接近、收益越大。07.06节Transpose的三段更均衡，所以收益更显著。
判断双缓冲值不值得做，可以先估算三段的相对耗时——如果某一段占绝对主导，
优化重点应该放在压缩那一段本身（比如减少搬入的数据量），而不是流水重叠。
任务5之后 aiv_vec_time（1.09μs）已远小于 aiv_mte2_time（2.61μs），瓶颈
就在MTE2搬入，这也是继续优化的方向。

【问题4】如果把窗口从 4x4（不重叠）改成 4x4 但步长为2（相邻窗口重叠一半），
UB中转的收益会变大吗？

会变大，而且这是本作业中UB中转唯一能真正发挥价值的场景。

关键在于数据复用。原题窗口不重叠，每个输入元素只被读取一次，总读取量恰好
等于输入规模（1M个元素），不存在任何复用——这正是任务4引入UB中转却几乎
没有收益的根本原因：UB的核心价值是"一次搬入、多次读取"，而零复用意味着
这个价值无处施展，MTE只是把同样的GM开销从vector流水搬到了MTE2流水。

步长改成2以后，相邻窗口在横向和纵向各重叠一半，每个输入元素会被大约4个
窗口用到（横向2个 x 纵向2个）。此时如果仍然直接读GM，同一个元素要从GM
重复读取约4次，总GM读取量膨胀到约4M次；而如果先用MTE把band批量搬入UB
（搬入量不变，仍是每个元素搬一次），后续那约4次读取全都落在UB上——片上
访问，延迟比GM低一个量级。UB中转此时消除的是"重复的GM访问"，这是实打实
的收益，不再是开销转移。

顺带一提，band的划分也要跟着调整：步长2时一个band需要包含4行输入但只
前进2行，相邻band之间有2行重叠，搬入时要把这部分重叠行一起搬进来。

这个对比正好回答了"UB什么时候值得用"这个更一般的问题：UB的价值来自数据
复用或访存模式转换（把非连续的GM访问转移到UB内部，如07.05的Transpose），
而不是"用了UB就会更快"。MaxPool原题两个条件都不满足——访存本就连续、
窗口零复用——所以UB中转拿不到Transpose那样的收益。

三、几个容易被忽略的补充结论
============================================================

1. 优化的收益不是手段的固有属性，取决于"还剩多少空间给它"。
   任务3 → 任务4 是本作业最值得记住的一组数据：引入MTE + UB中转让
   aiv_vec_time 降了66%，总耗时却基本没变。同一个改动，如果放在未做访存
   优化的任务2之后，看起来会是一次30%以上的巨大胜利；放在任务3之后就几乎
   归零。两项优化如果针对的是同一份底层开销（这里都是GM访存效率），收益
   不会叠加。汇报优化效果时务必说明基线，看别人的百分比时务必追问基线。

2. 开销可以被转移，转移不等于消除。
   任务4把GM访问从vector流水移到MTE2流水（vec降2.36μs，mte2涨2.56μs），
   总账几乎不变。看流水分项数据时，某一项大幅下降不代表优化成功，要确认
   它没有等量地涨到别处去。

3. 线程映射决定访存模式，访存模式决定性能——即使总工作量不变。
   任务3相对任务2，GM元素读取总次数完全相同、warp指令数反而更多（多了两条
   shfl指令和一次写回判断），却快了约45%，是全程收益最大的一步。差别只在
   同一warp内32条lane的地址是否连续：任务2的 local_col * WINDOW 步长为4，
   一条读指令跨越128个float = 512字节、命中4段；任务3的 in_col 连续，一条
   读指令只覆盖连续的32个float = 128字节、命中1段。在SIMT模型下，一个warp
   的一条读指令会被硬件合并成尽可能少的访存事务，地址分散时同一条指令要
   拆成多个事务，延迟成倍增加。
   遇到"每个线程处理一个输出、串行遍历输入窗口"的写法时，都值得检查一下
   同warp相邻lane的访存地址是否连续。

4. 同一件事，用哪个硬件单元做，结果可能差好几倍。
   "引入UB中转"这同一件事，若由SIMT线程逐元素从GM搬到UB，实测约16.7μs
   ——比任务3的直接读GM慢一倍多，因为逐元素搬运既没有MTE的批量传输能力，
   又额外增加了一次完整拷贝和一次 asc_syncthreads() 同步。交给MTE批量搬
   则至少不亏（持平）并为流水重叠铺路。数据路径完全相同，差别只在搬运单元。

5. 测量方法要匹配你要分辨的差距。
   任务3和任务4的差距在噪声量级，单次 msopprof Task Duration 完全无法
   区分，甚至会给出相反的排序（本机实测 7.957 vs 7.938μs）。差距在10%以内
   时，用host侧多次交替测量的均值，或者看稳定得多的流水分项数据。注意是
   "交替"测量——连续跑完A再连续跑完B，环境漂移足以凭空造出5%的差异。
   另外，刚编译完的第一次运行可能报出明显偏高的数值，应当丢弃。

6. 排除干扰因素。
   任务3把每个Block的线程数从256提到了1024，收益是否只是并行度上升？
   对照实验：保持任务2的线程映射不变、只把每个Block负责的band数增加到4
   （线程数同样上升），实测反而更慢。这才能确认任务3的收益来自访存形态。
