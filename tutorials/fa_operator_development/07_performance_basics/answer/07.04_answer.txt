07.04 优化步骤①均衡性 —— 小测验答案

1. CoreWeight 与有效块计数：
   - CoreWeight = 所有 B × 所有 N 的总（有效）基本块数 / 总核数，即每核期望负载 coreWightTarget。
   - mask 场景必须按有效块计数：因果掩码下每个 S1 行的有效 S2 块数不同（对角线以下），若按形状块数计数，分到的「名义负载」相同但真实工作量差数倍——均衡直接失效。GetCutBlockNums 把右上角/左下角被完全遮盖的块从总面积里减掉，才得到真实工作量。

2. 六个数组与按行分配：
   - 六个数组记录每个核的：S1 块（Spos）起始/结束、B（Sid）起始/结束、N（Nid）起始/结束——kernel 侧按核号查表即知道自己负责的 (B, N, S1) 区间。
   - 按行（S1 块）整块分配：每个 S1 块是一次完整的 softmax 归约单元（m/l 状态属于整行），劈到两个核就需要跨核归并；整行给一个核，核内自己跑 S2 循环，简单且无通信。

3. 切核判定的含义：
   - `sInnerBlockNums - dif > dif` 即「当前行的块数超过剩余缺口的两倍」才切核。
   - 避免的问题：把一行劈到两个核（跨核的 softmax 归约、复杂的边界处理）；
   - 代价：负载是离散的行粒度，最差核会超出期望负载（模拟实验里 1.47 倍）——行粒度越细（S1 块越多、BN1S1 细分）抖动越小，这就是细粒度分核更均衡的原因。

4. FlashDecode（切 S2）：
   - 触发场景：KV_length >> Q_length（Q 常为 1、KV 累积上万 token）且 batch 小——B×N×S1 的并行度远小于核数，大量核分不到任务。
   - 代价：softmax 分母是全序列的 l，切 S2 后每核只有局部 m/l/输出，需要 combine 归并——拆两段 kernel + 中间结果落 GM + 再启动；只有并行度收益大于归并代价时才划算（长序列 decode 正是如此）。
